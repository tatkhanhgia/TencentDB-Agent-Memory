TDAI Memory — Harness Onboarding

How to connect any coding agent (Claude Code, Cursor, Windsurf, OpenCode, Codex, Grok Build) to the TencentDB Agent Memory system. Written for both humans and agents: every config block is copy-paste ready.

🇻🇳 Tóm tắt nhanh: Kết nối harness vào memory chỉ cần 3 bước — (1) trỏ MCP command vào wrapper stdio tdai-memory-mcp.sh (không token, không port; identity tự chọn theo project), (2) thêm rules dạy agent gọi tdai_memory_context đầu session, (3) (tuỳ chọn, chỉ Claude Code) gắn hook SessionEnd để tự đúc bài học khi đóng session. Memory là read-only qua MCP — agent không bao giờ tự ghi. Muốn dùng thêm Skill (SOP tái sử dụng) thì xem mục 5 — bật cờ và dạy agent đi tìm, thiếu vế nào cũng không đủ.

1. Architecture in 30 seconds

READ (live, every session) ┌─────────────┐ MCP stdio wrapper ┌──────────────────┐ ┌─────────────┐ │ Harness │ ───────────────────────▶ │ MemoryMCP │ ───▶ │ MemoryCore │ │ (any agent) │ per-project identity │ read-only tools │ │ :8420 │ └─────────────┘ (_identity.sh) └──────────────────┘ │ L0→L1→L2→L3 │ │ └─────────────┘ │ WRITE (only at session end, only via hook) ▲ └── SessionEnd hook ──▶ tdai-reflect CLI ── extracts ≤3 lessons ─────┘ (same _identity.sh routing; writing nothing is the normal outcome)
  • Reads go through a read-only MCP server. Four tools, nothing can mutate memory.
  • Writes happen only when a session ends: a hook runs tdai-reflect, which extracts at most 3 durable lessons (ADRs, constraints, preferences) — or, most of the time, nothing. Agents must never write memory directly.
  • Memory layers: L0 raw lessons → L1 atomic memories → L2 scene files → L3 persona. Consolidation is automatic. All outputs are always English.

2. Step 1 — Point your harness at the MCP server

stdio The standard transport — every harness

One config for everything: point the MCP command at the stdio wrapper. No token, no port, no daemon to keep alive — the wrapper sources its environment from deploy/global-images/.mcp.env and picks the right memory identity for the project it is launched in (see the box below).

Claude Code — project .mcp.json, or ~/.claude.json user-scope (one config for every project on this machine; the wrapper re-resolves identity per project anyway):

{
  "mcpServers": {
    "tdai-memory": {
      "command": "/Users/mac/Documents/Projects/MyProjects/TencentDB-Agent-Memory/deploy/global-images/tdai-memory-mcp.sh"
    }
  }
}
Cursor — ~/.cursor/mcp.json (or project .cursor/mcp.json) 
{
  "mcpServers": {
    "tdai-memory": {
      "command": "/Users/mac/Documents/Projects/MyProjects/TencentDB-Agent-Memory/deploy/global-images/tdai-memory-mcp.sh"
    }
  }
}
Windsurf — ~/.codeium/windsurf/mcp_config.json 
{
  "mcpServers": {
    "tdai-memory": {
      "command": "/Users/mac/Documents/Projects/MyProjects/TencentDB-Agent-Memory/deploy/global-images/tdai-memory-mcp.sh"
    }
  }
}
OpenCode — project opencode.json 
{
  "mcp": {
    "tdai-memory": {
      "type": "local",
      "command": [
        "/Users/mac/Documents/Projects/MyProjects/TencentDB-Agent-Memory/deploy/global-images/tdai-memory-mcp.sh"
      ]
    }
  }
}

Codex uses the same command in ~/.codex/config.toml — see examples/codex/config.toml. Per-harness details live in each examples/<harness>/README.md.

The wrapper sources its own environment. Do not add an env block to the config — a stray TDAI_MCP_HTTP_PORT would flip it into HTTP mode and break stdio.

How the identity is chosen (automatic, per project)

One project = one agent. At startup the wrapper resolves the identity for its working directory with deploy/global-images/_identity.sh — the same resolution the write hook uses, so a session always recalls the store its lessons are written to:

  1. .tdai-project.env at the project root — explicit override (TDAI_AGENT_ID=agt-…; write it by hand with the agent id from the Panel, or run sync-memory-identities.sh --link <project-dir> <agent-name>).
  2. Folder-name convention (zero setup) — an active Panel registry agent whose slugged name matches the project folder name. Name the agent after the folder and reads and writes both route themselves.
  3. The machine default from .mcp.env.

The chosen route is logged to stderr (identity route=… agent=…), and the final agent id is validated against the registry — a stale .tdai-project.env warns instead of silently binding to a dead agent.

Two things agents often miss: (1) MCP configs and identity are read at session start — after writing the config or .tdai-project.env, the current session cannot use it; open a new session (or reconnect MCP). (2) A brand-new long-lived project should usually get its own agent (see "Adding a new agent/project" in §6) instead of piggybacking on the machine default.

HTTP Legacy, opt-in — remote access / in-session identity picker

A Streamable HTTP daemon (:8425, Bearer device token from .mcp.bindings.json, in-session picker via tdai_identity_list/tdai_identity_use) still exists but no longer starts by default — run ./start-memory-mcp.sh (or MCP_HTTP=1 ./start-all.sh) only when stdio genuinely cannot work, e.g. a harness on another machine.

3. Step 2 — Teach the agent to use memory (rules)

Append this to the harness's rules file (never replace existing rules) — CLAUDE.md, AGENTS.md, .cursorrules, .windsurfrules… Ready-made snippets: examples/rules/.

# TDAI memory (read-only)
At session start, call `tdai_memory_context` once to load team memory
before non-trivial work.
When a task references past decisions or conventions, use
`tdai_memory_search` (and `tdai_scene_read` for the full scene) before
re-deriving from scratch.
Do not write memory yourself. Capture runs automatically at session end
via a hook, not the model.
Do not dump memory contents verbatim into files or commits.

4. Step 3 (optional) — Enable the write path

Only Claude Code has a SessionEnd hook today. Other harnesses stay read-only, which is fine.

// .claude/settings.json (project) or ~/.claude/settings.json (global)
{
  "hooks": {
    "SessionEnd": [
      { "hooks": [ {
        "type": "command",
        "command": "/Users/mac/Documents/Projects/MyProjects/TencentDB-Agent-Memory/deploy/global-images/hooks/tdai-reflect-hook.sh"
      } ] }
    ]
  }
}
  • The hook is fire-and-forget (always exits 0, runs detached). Log: deploy/global-images/.reflect.log.
  • Sessions shorter than 6 text turns are skipped. Extraction uses the local LLM (LM Studio, 127.0.0.1:1234) — it must be running with the model loaded, or the hook logs an error and writes nothing.
  • Writes are idempotent: re-running reflect on the same session never duplicates lessons.
  • Per-project write identity — the hook calls the same _identity.sh resolution as the stdio wrapper (§2): .tdai-project.env → folder-name ↔ registry agent → machine default. Reads and writes therefore always land on the same agent. The .reflect.log line shows which route was used (route=file|folder-name:…|default).

5. Step 4 (optional) — Skills

Skills are a different asset from memory: reusable SOPs the team already proved out — a release checklist, a debugging routine, a setup procedure — each with versions, resource files, trigger boundaries, and validation rules. Memory tells the agent what the team knows; a Skill tells it how the team does this.

Off by default. One edit turns it on:

# deploy/global-images/.mcp.env
TDAI_ENABLE_SKILLS=true

Stdio wrappers read .mcp.env at launch, so just open a new session (reconnect MCP). Only the legacy HTTP daemon needs an explicit restart (./start-memory-mcp.sh).

Four read-only tools appear. Writes stay in the Panel and MemoryProxy — nothing here can create or modify a Skill.

ToolWhat it does
tdai_skill_listThe catalogue — no query needed. Same scope rule as search. The agent needs this to learn what exists at all.
tdai_skill_searchKeyword search (BM25 over name, description, body). Defaults to the active identity's own Skills; scope: "team" drops the owner filter and searches the whole team library.
tdai_skill_getFull SKILL.md plus a manifest of the files attached to it.
tdai_skill_file_readOne file from that manifest, e.g. scripts/run.sh.

The flag alone is not enough. Two things about the MCP path routinely surprise people:

  • Nothing enumerates Skills for the agent. It learns the catalogue only by calling tdai_skill_list; a blind keyword search can miss a Skill worded differently from the task.
  • Nothing auto-injects Skills. MemoryProxy pushes an <available_skills> catalogue into every system prompt; MCP is pull-only. The agent finds a Skill only if it decides to search — so it needs to be told to look.
  • Nothing executes a Skill. It is a procedure the agent carries out with its own tools, not a program that runs itself.

So pair the flag with guidance, the same way Step 2 pairs the transport with rules:

  • Claude Code — cd deploy/global-images && ./install-claude-skill.sh installs MemoryMCP/skills/tdai-memory/SKILL.md into ~/.claude/skills/. It carries the full workflow (list the catalogue → search when it is large → get → read manifest files) and loads on demand, so it costs nothing until relevant. Restart Claude Code afterwards.
  • Every other harness — the Skills paragraph already included in examples/rules/. That format is Claude-Code-only, so for Cursor / Windsurf / Codex / OpenCode the rules file is the only guidance they get.

Skip both and the agent still has the tools — it just has to infer from the tool descriptions when to reach for them.

6. The identity model

Every memory record is isolated by team / user / agent. There is no "project" dimension — one project = one agent. A session reads exactly one agent's store, resolved automatically at server startup from the project directory (§2: .tdai-project.env → folder-name ↔ registry agent → machine default). The Panel agent registry is the single source of truth; the resolved id is validated against it.

The in-session picker (tdai_identity_list / tdai_identity_use, MCP elicitation) exists only in the legacy HTTP mode — on stdio there is nothing to pick.

Adding a new agent/project later

  1. Create the agent in the Panel (http://127.0.0.1:8125), named after the project folder — that's it: the next session in that folder reads and writes that agent's store. No commands, no config changes.
  2. If the folder name can't match the agent name, run deploy/global-images/sync-memory-identities.sh --link <project-dir> <agent-name> once — it writes the project's .tdai-project.env (or write that file by hand: TDAI_AGENT_ID=agt-…).
  3. Reconnect the MCP server (new session) — identity is resolved at startup.

8. Troubleshooting

SymptomCause → fix
Session reads the wrong agent's memoryCheck the wrapper's stderr line identity route=… agent=… (and .reflect.log for the write side). Wrong route → add/fix .tdai-project.env or rename the Panel agent to match the folder, then open a new session — identity is resolved at startup.
[tdai-identity] warning: … not found / not activeThe resolved agent id is stale — the Panel agent was deleted, archived, or the .tdai-project.env id is wrong → fix the file or restore the agent.
Connection refused on :8425 (legacy HTTP)The HTTP daemon no longer starts by default → use the stdio wrapper, or run ./start-memory-mcp.sh deliberately (--status for health).
401 unauthorized (legacy HTTP)Wrong/missing Bearer token → re-read the device token from .mcp.bindings.json.
identity_not_selected error (legacy HTTP)Normal on multi-identity tokens without a default — pick via the dialog, or call tdai_identity_use. Not a failure.
Session not found / re-initializeThe MCP server restarted (sessions are in-memory, 60-min idle expiry) → the client reconnects automatically on the next call.
Hook ran but no lessons appearCheck .reflect.log. "skipped" = session too short or nothing durable (normal). LLM timeout = LM Studio not running/slow — the hook allows 240s by default.
Skill tools missing / skills_disabledTDAI_ENABLE_SKILLS still false, or the session predates the edit → fix .mcp.env, open a new session (legacy HTTP: re-run ./start-memory-mcp.sh).
Skill tools present but the agent never uses themExpected — MCP does not auto-inject Skills. Install the Claude Code skill (./install-claude-skill.sh) or paste the Skills paragraph from examples/rules/ into the harness's rules file.
tdai_skill_search returns nothing you can see in the PanelTwo separate causes: default scope is the active identity's own Skills → retry with scope: "team"; and matching is BM25 keywords → fall back to tdai_skill_list, which needs no query.
stdio server exits immediatelyMissing env → the wrapper needs .mcp.env filled in and MemoryCore running (it falls back to .admin-key for the API key).
Sanity check for a new setup: open a fresh session and ask the agent "what do you remember about this team's architecture decisions?" — it should call tdai_memory_context and answer from memory, not from guesswork.
